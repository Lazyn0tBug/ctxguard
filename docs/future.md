## 后续候选：需要条件成立才启动

| ID | 候选 | 启动条件与必须验证的内容 |
|---|---|---|
| F1 | tgrep / trigram 内容索引 | 大仓重复查询中实时扫描仍是主要成本；测冷建索引、暖查询、磁盘占用、内存、修改到可检索延迟及无字面量模式 |
| F2 | fff 文件发现与模糊检索 | 有明确的路径模糊发现/相关性排序需求；作为独立能力暴露，精确 search 不自动回退 fuzzy；验证 PCRE2 固定引擎约束能否满足 |
| F3 | 常驻搜索上下文 | 反复查询收益覆盖初始化、监听与缓存成本；明确多项目、多会话的状态隔离、退出与内存回收 |
| F4 | PCRE2 硬墙钟超时 | match/depth 等资源上限不足以满足交互时延要求时，使用可终止 worker；验证取消、清理、部分结果与主进程存活 |
| F5 | 跨入口统一预算 | 用户需要 hook 与 MCP 共同累计时，先定义 session/agent/compact 语义，再实现事务化扣费；本轮保留现有分离状态 |
| F6 | 并发会话状态与失败策略 | 有并发扣费丢失或状态损坏复现时，考虑 SQLite 事务或锁；分别决定配置、I/O、索引错误的行为，不随 Rust 化隐式更改 fail-open |
| F7 | 多平台发布 | 面向普通用户交付前验证 macOS arm64/x86_64、Linux gnu/musl、Windows 构建与依赖；发布流水线、校验和及升级回退 |

索引加速必须定义新鲜度：候选文件最终校验不能找回因过期索引漏掉的命中。
引入 F1/F2/F3 前，需明确修改文件补扫、删除处理、监听丢事件恢复和扫描回退；初始索引未完成不能返回“完整无命中”。

## 评估依据

- [ripgrep 搜索组件](https://docs.rs/grep/) 与 [PCRE2 Matcher](https://docs.rs/grep-pcre2/)：本轮已选，待实现。
- [tgrep](https://github.com/microsoft/tgrep)：trigram 加速与索引生命周期候选，不作为本轮默认后端。
- [fff](https://github.com/dmtrKovalenko/fff)：常驻文件/内容检索与模糊发现候选，不直接替换当前精确 search 契约。

项目自带跑分仅作线索；选型依据应为同一 ctxguard 文件范围、相同匹配语义与相同完整性要求下的实测。
